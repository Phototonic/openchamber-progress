# Design

## 1. Existing owners and constraints

- **The ordinary list read pages by offset.** A refresh reads up to ten pages of 50 plans. The read is complete when the last page had no continuation. Offsets are not a snapshot: a plan that leaves the list behind the cursor between two pages moves the next unseen plan behind the cursor, and the list envelope carries no change token.
- **A complete list supplies bulk targets without a read.** Tidy and Select all count from the loaded rows when the list is complete. Otherwise a bounded scan reads the scope; each later page of that scan re-reads the previous page's last plan, the count fails when that plan is not there, and a count that crossed any page boundary already says that plans may have been missed.
- **Search keeps two result pages.** Each poll, a freshness read checks the plans of the page shown and the opened plan by point lookup. A plan that is gone leaves every retained page. The first page of a search starts checked, because the search has just read its hits, and a retained page shown again counts as checked once a reply covered it. The board treats only a checked page as evidence of which plans are in view.
- **A Select all rule holds two kinds of absence.** Plans the person deselected, and plans a cleanup receipt took out of view. Both are merged when an action captures the rule.
- **A single-plan cleanup is bound to its account and store.** If either changed when its reply arrives, it clears its own state and touches nothing else. The bulk run stops sending on such a change, but its completion still resets caches and applies its receipts to the board shown then.
- **How a frame learns of a switch.** The host announces an account change. A store or binding change arrives with a list reply. List reads pause while a bulk run is in flight and its panel is kept, and continue during a single-plan request. A change of the board's filters or search during the run ends that panel, so list reads resume while the request in flight is still held. Every cleanup request names the store it was counted in, and the service refuses one that names another store.
- **Each remembered list scope keeps the health reply it arrived with.** Showing a remembered scope while its new read is pending adopts that health reply, including its cleanup facts, in place of the current one. A refresh reads health before its list pages, and the controller accepts that health reply when the refresh settles.
- **Two paint lanes.** An explicit action repaints at once, replacing even a held control. Background data waits while a control is held or a picker is open. A cleanup focus request is queued and applied at the next paint that contains its target.
- **The bulk run engine keeps receipts only.** The per-plan request already classifies its failure; the run drops that and reports every plan without a receipt as skipped. The single-plan path already says "could not be confirmed" for an uncertain failure.
- **The large-library gate** compares idle traffic per complete refresh, using requests in the order they were sent, and falls back to wall-clock counts for older artifacts. The driver's request log records every request with its frame, method, path, query and time, and nothing about what caused it. Its reply log holds the same routes but records a request only when it is answered, so it cannot order or bound traffic by when it was sent.
- **A structural plan revision keeps an explicit blocked status.** Removing a prerequisite does not unblock the task that waited on it.

## 2. Counts and selection while plans change

**Decisions.**

1. **A count taken from a list read in more than one page is qualified.** The list read records that it crossed a page boundary. A Tidy or Select all confirmation built from such a list carries the existing line that some plans may have been missed, on the first step and on the deletion step. A list read in a single page is one answer from the service and stays exact. Rows explicitly chosen from the loaded list stay exact: they name their plans and are not a census. A Try again recount names its plans too, but on a complete list it is taken by looking those plans up among the loaded rows. It stays exact when it found every plan it names, or when the list was read in one page, where a plan that is not there has left. When the list was read in several pages and a named plan is not among the rows, the read cannot show whether that plan left or was missed, and the recount carries the same line. Where chosen rows or a recount are counted by a scan instead (a searched or truncated scope), the scan's existing qualification and Check more rules apply unchanged. That includes an older service, whose scan pages the list by offset and cannot vouch for what crossed its cursor. The qualification is on the confirmation line only. The selection bar keeps the 1.5.1 plus rule: under Select all its count is the number of selected plans the frame has loaded, with a plus only while matching plans are known not to be loaded. It is not a verified total, and it is the confirmation that says so before any request. No read is added and the ordinary list read is unchanged.
2. **A freshness reply certifies only the page it was asked about.** The page's identity is its number in the run, not its position among the retained pages. When Load more drops the oldest retained page, a reply still in flight is never credited to the page that took that position. Whether it still certifies its own page, if that page is retained and shown again, follows the existing retirement rules; this change adds a prohibition, not a new way to be credited. A reply certifies a page only when it covered every plan the page shows when the reply arrives: a search still running can append hits to the page a reply was asked about, and those plans were not covered. The rule runs one way. Hits the search reads into a page after a reply certified it leave the page checked: they were read from the service at that moment, which is what the first page of every search rests on, since it starts checked and is filled only by such reads. A reply is needed for hits that were carried over: a retained page shown again, or hits held back from an earlier read and placed on a new page. The frame does not record which hits of an unchecked page were carried over, so a reply certifies such a page only when it covered all of its plans. Recording coverage per hit would make the two orders equal and is listed as a follow-up. The next poll covers the plans read since.
3. **A cleanup in this frame retires freshness checks in flight.** Retiring the search after a cleanup action in this frame also retires any freshness read the frame already sent, so a reply from before that cleanup cannot mark a page checked or undo what a receipt established. The boundary is this frame's own invalidation. A cleanup made in another frame retires nothing here: a freshness reply that shows its effect is the evidence decision 4 acts on.
4. **Removal is a fact about a plan, not about a page.** When a freshness reply shows a plan missing, deleted or on the other side of the archive boundary, its hits leave every retained page, as today, and the selection forgets it, whether or not the page shown was the one the reply certified.
5. **Deselection and departure are separate.** A deselection lasts until the person changes it or the selection ends. A departure ends when an Undo receipt returns the plan, when a verified read lists it, when the person clicks its row, or when a fresh count finds the plan in the view at a newer cleanup generation than the one that took it out. A plan archived here and restored elsewhere is therefore counted by the next action. A return by receipt, read or count ends the departure only. If the person had also deselected that plan, it stays out as a deselected plan until the person clicks its row. Of the events that return a plan, that click is the only one that also ends a deselection. Pressing Select all again is a different thing: it replaces the selection, and so clears deselections and departures alike, as it does today. The generation that took a plan out is the one its receipt returned. The run hands it to the selection together with the receipt, as a map from plan to cleanup generation where it handed over a set of plans before. It is not read from a loaded row, because Select all can archive a plan the page never loaded. A cached, unchecked page is still no evidence.
6. **A newly opened result page starts unchecked**, whatever the state of the page shown before it, and becomes checked when a freshness reply covers its own plans. Visible consequence: the note that results are being checked can show on a new page until such a reply succeeds. No time limit is promised: the poll backs off after a failure and pauses while the frame is hidden. A failed freshness read leaves the page unchecked and is reported by the existing stale indication. A page that shows no plan has nothing to check: when Load more ends without a hit for the new page, no freshness read is added for it and the checking note is not shown.

**Consequence of decision 1.** Where the scope's list spans more than one page (more than 50 plans), the Tidy and Select all count line always says that some plans may have been missed. The line is honest and the wording exists in three languages; it is also more visible than before. The maintainer accepted it as the usual line above one list page. Removing it needs a list read the service can vouch for as a snapshot, which is out of scope.

**Alternatives rejected.** Re-reading the previous page's last plan in the ordinary list read: ten pages would then load 491 plans instead of 500, changing the documented bound and the reference library's measurements. Running the bounded scan for every multi-page list: it adds up to eleven reads to each opening and still ends with the same qualified line. Treating two identical consecutive list reads as verification: strong evidence, not proof, and a new rule for a patch release.

## 3. Account, store and capability

**Decisions.**

1. **A bulk run completes only into the account and store it ran in.** The run captures the integration account and the store and binding identity when it starts. If the frame observed a change of either since the run started, the run drops its own state when it finishes and changes nothing on the board shown: no cache reset, no selection change, no closed plan, no result line. The test is whether a change was observed, not whether the identity is equal at the end: after a switch away and back the board shown was loaded anew, and the person may have opened or selected a plan on it. The result line is not what changes: the 1.5.1 scenario said the result reports what completed after any context change, but the interface shipped, and is tested, without a result line after an account change or a change of board scope. The confirmation requirement is modified to state that outcome. What changes in behaviour is the rest of the list: today such a run still resets caches and applies its receipts to the board shown then. A change of board scope inside the same account and store keeps the outcome the 1.5.1 interface has: the run stops, shows no result line and sends its one reconciliation read when it ends. Changing the filters or the search is itself the next action, which ends a result. No behaviour changes for that case. One effect of a run is device-side and survives the change: a validated Delete receipt removes the review marker stored for its plan under the account and store the run started in, also when the receipt arrives after the change, as it does today and as the single-plan path does. That marker is keyed by account, store, binding, source and plan. It can therefore reach a review open on the board shown only when that board is the same account and store again and shows that same plan, which the receipt has just proved deleted; ending that review is correct, and no further guard is added for it.
2. **Cleanup support is what the service last said, whichever list is shown.** The controller keeps the cleanup facts of the latest health reply it accepted apart from the remembered lists. Adopting a remembered scope changes the list shown and never those facts, in either direction: it does not bring back support, or in-progress support, that a later health reply withdrew, and it does not hide support that a later health reply granted. Support returns only with a newer health reply that offers it. A health reply is accepted when the refresh that read it settles, complete or failed, as today. One that arrived inside a refresh still reading its list pages takes effect when that refresh settles; until then a request is checked when it is sent and by the service. Applying it earlier would change the list read itself and is not part of this change.
3. **An account or store switch releases the busy state.** Cleanup controls on the new board are usable without waiting for a request sent before the switch, and that request's late completion can neither complete nor release a newer run. The busy state and the stale-answer cleanup are bound to the request that set them, in the single-plan path as well as in the bulk run: both share one busy state today, and a late single-plan answer clears it and resets the cleanup panel whatever is running by then. Comparing the account and store alone is not enough, because it reads a switch away and back as no change.

**What counts as a switch.** Decisions 1 and 3 act on a change the frame has observed. An account change is observed when the host announces it, during any request. A store or binding change is observed with a list reply. Those continue during a single-plan request, so a store change is observed while that request is held. They pause during a bulk run for as long as its panel is kept, so a store change with no account change is then observed by the list read that follows the run. Until then the board shown is still the one the run started on, the run ends there, and that read then adopts the new store and clears the board, as today. The requests of such a run name the old store, and the service refuses them. Observing a store change while list reads are paused needs a read the run does not send today and is listed as a follow-up. The pause ends early when the person changes the board's filters or search during the run: that ends the run's panel, list reads resume while the request in flight is still held, and a store change one of them shows is an observed change, to which decisions 1 and 3 apply.

**Not covered: support withdrawn while an action is open.** Decision 2 governs what the controls offer. A count, confirmation or run that is already open when in-progress support is withdrawn is not re-checked by this change. A bulk run decides whether it may send in-progress plans when it starts and leaves them unsent otherwise; a single-plan deletion attaches the in-progress acknowledgement only if the service still offers it when the request is sent; and the service's own check refuses the rest. Losing cleanup support altogether already retires an open confirmation. Re-checking open counts and confirmations on a downgrade is listed as a follow-up.

**Mixed versions and rollback.** Interface only. Nothing is stored, and no request changes.

## 4. Background updates and focus

**Decisions.**

1. **A count that finishes by itself is background data.** The end of a scan, its failure and the end of a Check more continuation repaint through the background lane, so they wait for a held control or an open picker like any refresh. Opening the panel, Cancel, the confirm buttons and pressing Check more are explicit actions and still repaint at once.
2. **A run's own updates are background data too.** That covers each progress update and the repaint at the end of the run, with its result line and the selection changes its receipts cause: like a count, a run finishes by itself. A press on Stop is not lost to a progress update, and neither update replaces a held control. The progress line and the result line can lag while a control is held or a picker is open. Nothing else waits: the run, the release of its busy state, the cache invalidation and the reconciliation read happen when the last reply arrives. Starting a run, Stop, Undo and Try again are explicit actions and still repaint at once. Two limits follow from what does not wait. First, the cache invalidation at the end of a run retires the controls of the board whose data it invalidated, as every cache reset does: a Filters button held at that moment stays in place, so focus and the pointer are not disturbed, but it ignores that click. Keeping such a control valid across the reset is listed as a follow-up. Second, a result has to be shown before a refresh can expire it: a refresh does not expire a result that has not been painted yet, so a hold that lasts past the next refresh loses neither the result line, nor its unconfirmed warning, nor Undo. Once painted, the result expires with the next refresh and that expiry repaints at once, as in 1.5.1; and an action of the person that changes the view ends a result whether or not it was painted. Both are listed as follow-ups.
3. **A deferred focus move is decided when it is applied.** The move to the Tidy button after a run that ended with focus on Stop, and the move to Cancel after a count, are applied only if focus is still on the control the move was queued from, or is on no control because that control was removed. Being inside the cleanup panel is not enough: once Stop is gone the result line can offer Undo while the Tidy button is still absent, and a person who has moved to Undo keeps focus there. If the person has focused anything else meanwhile, in the panel or outside it, the request is dropped, not kept for a later paint. A request denied because another frame has focus stays dropped, as in 1.5.1.

No timer is added and no freshness is deferred beyond the existing press and picker rules.

## 5. Unconfirmed results

Each target of a run ends in exactly one of three states.

| State | When | Result line |
|---|---|---|
| Done | its receipt was validated | archived, restored or deleted |
| Skipped | the service answered and refused it (changed, closed, reused operation, not found, store busy); or the view left it out right before sending; or the run stopped before sending it | skipped |
| Unconfirmed | the request was attempted and no valid answer came back: a lost or timed-out reply, a connection or host failure, or an answer that is not a valid receipt or one of the refusals above | could not be confirmed and may have been archived, restored or deleted |

The split follows the classification the single-plan messages already use, so one failure never reads as "changed" on one surface and "possibly applied" on the other. A failure that fits neither refusal class counts as unconfirmed: over-warning is safe, under-warning is the defect. A target the run did not attempt, because the view left it out or the run stopped first, is never unconfirmed. An attempt that fails before the service could receive it, while the request is prepared or handed over, counts as unconfirmed too: the run engine cannot tell it from a lost reply, it does not happen in normal operation, and telling the two apart would need a second failure channel for a case that only over-warns.

**Result line.** Still one sentence, announced once. English reference strings:

| Case | Text |
|---|---|
| All done | 128 plans archived. |
| Some skipped | 126 of 128 plans archived; 2 skipped. |
| Some unconfirmed | 126 of 128 plans archived; 2 could not be confirmed and may have been archived. |
| Both | 125 of 128 plans archived; 1 skipped; 2 could not be confirmed and may have been archived. |

Delete and restore use "may have been deleted" and "may have been restored". Russian and Simplified Chinese ship in the same pull request, as whole strings with plural rules, and are checked by reading.

**Undo and Try again.** Undo restores exactly the plans with a validated archive receipt, each bound to the generation its receipt returned. An unconfirmed plan has no receipt and no generation, so it is never part of Undo. If its archive was applied, it can be restored on its own once an Archived plans list or search shows it. The reconciliation read is not promised to show it: that read uses the scope shown, which leaves archives out during an ordinary archive run, and an Archived plans list has the ordinary page limit. After an archive, a deletion or a restore of selected plans, Try again recounts skipped and unconfirmed plans together under the existing retry rules, which leaves out the ones that have left the view. After a partial Undo it does not recount: a plan whose restore did not arrive is still archived and would not be in the view shown, so Try again sends the same restore request again for exactly the remaining plans, each still bound to the revision and cleanup generation its archive receipt returned, as it does today. The service answers a repeated request from the receipt it saved for that request, before it compares generations: a plan whose earlier restore was in fact applied is therefore confirmed as restored, and is not restored twice. A plan that another cleanup changed since is refused, because its generation has moved, and is reported as skipped. Nothing is retried automatically, and the one reconciliation read after the run is unchanged.

**QA driver.** The selection driver proxies the frame's requests through the cleanup fixture's request helper, whose three-second limit turned a slow reply into exactly this unconfirmed case and let the driver continue to Undo with fewer plans than it believed. The helper's limit for service calls becomes 30 seconds, its readiness probe keeps a short bound so a hung start still fails fast, and the driver asserts that the archive result reports every plan archived before it uses Undo.

## 6. Large-library gate

QA only. Nothing shipped changes.

1. **Exact window, counted by requests sent.** The request and reply offsets that bound a timed window are captured in the same browser evaluations that start and stop its timer. A request logged after the stop is not counted, and it does not close a refresh that was still open. Every count the comparison uses, the cadence counts and both inbox forms included, is taken from the request log inside those bounds, so a request counts by when it was sent: one sent before the window and answered inside it is out, one sent inside and answered after it is in. The reply log stays for what only a reply can show: status, size and timing.
2. **Run reads are counted per window, and their per-refresh budget is unverified.** A refresh can cause a run read after the next refresh has started: the automatic follow-up of a run reconciliation is sent without waiting for the next poll. In the request log that read looks like any other run read, so the gate cannot say which refresh caused it, and it does not try. Run reads are taken out of the per-refresh figures and counted once per window: every run read sent inside the window, whichever refresh preceded it, including one sent before the window's first list start and one sent after the last. Late traffic then cannot be charged to the wrong refresh, be lost with the final open refresh or be dropped at the start of the window. A window count does not show how many run reads one refresh sent: five reads over five list starts and five over four give the same count. The gate therefore shows each window's run-read count beside its list starts as an informational row and judges neither. Because the cause is the log, not a particular baseline, this is a standing limit rather than the unverified state of decision 7: the row never changes the exit status, so the gate can still pass. Tying each read back to the refresh that caused it would remove the state. It needs the shipped interface to label its requests, which these QA-only checks must not ask for, and is listed as a follow-up.
3. **The artifact says how it attributed.** An artifact records its attribution method. The gate does not treat an older artifact that bucketed replies as equivalent to one that buckets requests.
4. **The wall-clock inbox split is saved** beside the complete-refresh counts, so a window with a single list start still has a split to compare.
5. **The bundled inbox form is compared on its own** as well as in the combined figure, so an extra standalone request at a window edge cannot pay for an added first window on the list read. The form carried by the list read is counted per list start. A list start either carried it or did not, so that figure has no error at the window edge and is comparable in any window. The standalone form is judged in the combined figure over complete refreshes. A standalone request sent in the refresh still open when the window ends is counted in the window's split and changes no per-refresh verdict, like that refresh's list pages: a refresh the window cut is on neither side of a ratio.
6. **Health is outside per-refresh traffic.** The health read precedes its refresh's first list page, so it cannot be tied to a bucket; the cadence check already covers it.
7. **No comparable baseline means unverified.** When the baseline or too few candidates carry the inbox split, the combined inbox budget is reported as unverified. The same holds for any per-refresh budget whose baseline and candidate figures do not rest on the same denominator, even when both artifacts are in the current format. A window that completed no refresh has only wall-clock counts over a single list start, where the traffic of a refresh that began before the window changes the figure by itself: nineteen list pages over one list start would let a candidate reading eleven pages per refresh pass a ten-page contract. Such a figure is not compared with complete-refresh figures. The gate then reports neither a pass nor a failed budget and exits non-zero with that state named. The other comparisons still run. A baseline recorded with the current driver whose idle window completed at least one refresh removes the state for those budgets. Its summary names which budgets are unverified and which failed. The run-read row of decision 2 is informational and is neither.
8. **The tests tell the paths apart.** The attribution fixtures fail if requests were bucketed in reply order, and the gate fixtures use counts that differ per denominator and mix an older candidate, a current candidate and one without a split. They include a baseline with a single list start against candidates with complete refreshes, a run read on each side of the window's first and last list start, with the run-read row informational whatever those counts are and never changing the exit, and an inbox request sent across each window edge, with the window's split and the unchanged complete-refresh figures both asserted.

The driver is not part of portable CI. Decisions 1 to 7 put their logic in the attribution helper and the gate, which the unit tests cover; the browser-side capture of offsets is shown by one rendered run.

## 7. Guidance, receipt evidence and documentation

1. **A dependency block follows the plan's current prerequisites.** The moved-back sentence in the skill, the tool description and the inline guidance says to read the current plan before a handoff: once every prerequisite the task still has is done, the task blocked this way goes back to working or pending. A prerequisite the plan no longer lists no longer holds it. A skipped prerequisite that is still listed counts as unfinished. The rule stays limited to the task the agent blocked this way; a decision, review, external or other blocker is never touched. The store is unchanged: a structural revision still keeps an explicit blocked status, which is why the guidance has to say this. The tool description stays within its tested limits.
2. **Refusal guidance checks a receipt before reading meaning into it.** Before the coordinator refusal reader infers that cleanup retired a waiting delegation, it checks that the receipt's state agrees with its dispatch and its declared tasks, as the per-plan reader does: a pending declaration names no dispatch, a reserved one does, and both name at least one task. The check applies to pending and reserved receipts only. A cancellation is stored as retired and comes in two shapes, both read as before: the empty declaration that cancelled, and the earlier declaration it retired, which keeps its tasks. A receipt that fails the check makes the guidance incomplete, the existing explicit limitation, instead of producing a `closed` refusal. A well-formed receipt still yields no refusal once the plan's current assignment shows that its declared tasks were explicitly linked since; the check runs before that existing step and does not replace it. No receipt or store change.
3. **Point lookups are documented where they apply.** `docs/ui.md` says that chosen rows are validated by point lookup in a searched or truncated scope on a service that advertises task search, that a complete browse list uses the loaded rows, that an older service counts a truncated browse scope by list scan, and that the point lookup skips, and does not adopt, a plan whose revision moved where search or session criteria apply. That skip belongs to the point lookup only; item 4 says what the other two paths do.
4. **The retry baseline is named, for the reader that compares.** `docs/contracts.md` and `docs/ui.md` say that where the point lookup validates named plans, each is compared with the revision supplied to the count, which on Try again is the original target's revision, instead of "since the count began". The other two paths compare nothing against that revision and the guides say so: a complete list takes a named plan as its loaded row shows it, and an older service's list scan takes it as the scan's row shows it. In every path the service still checks the revision each request carries.

Items 3 and 4 change documentation only.

## 8. Stable system prompt section

1. **The system section holds only text that does not change within a session.** The companion's context hook adds one section to the system prompt on every eligible request. Today that section also carries the one-request hint after a dispatch, a plan-file write or a tracker save, the resume capsule of a sub-agent session, which names the plan's current revision and can drop out for one request when its bounded lookup times out, and the delegation refusal note. Each of these changes the system prompt between requests, and a provider prompt cache misses from the first changed byte, which takes the whole message history with it. After this change the system section is the fixed activation guidance only, byte-identical on every request where it is present.
2. **Changing text goes after the cacheable prefix, in a carrier valid for the latest message's role.** The hint, capsule and refusal note are added after the content of the latest message the request carries; the stored conversation is unchanged. The carrier depends on that message's role. On a user message they are a text part after its content. On a tool message, which is the latest message of a continuation after a tool call such as a plan-file write, a separate text part is not valid, so they are appended to the output of its last tool result, the same carrier the existing note on a completed tool result already uses and the native driver already checks. A tool message whose last result is not a string or text content, or is the Code Mode `execute` wrapper's exact script value, has no valid carrier, and neither has any other role: the text waits for the next request whose latest message has a valid carrier and is never dropped. The text and its eligibility rules are unchanged; only its position moves. Providers that drop plugin system sections now also receive these notes; the checklist they rely on is already in the tool description and does not change.
3. **A delivered note stays where it was put.** A provider writes its cache at the end of the latest message, which is where the note sits, and reads it only when a later request repeats that prefix byte for byte; with extended thinking, the reply's thinking is also bound to that prefix. So a note added to one request and absent from the next would cost the cache and the thinking of every request it was on. The companion therefore remembers, per session, each note it delivered with its carrier: a tool carrier by its call identifier together with its position and a digest of its original output, because providers do not keep call identifiers unique across turns; a user carrier by the message's identifier when it has one, or else by its position and a digest of its original content. On every later request whose messages still hold that carrier, it adds the same text in the same place, so each request's messages are the previous request's messages followed by new ones, and the stored conversation still never changes.
   - **Notes due together are one note**: hint, then capsule, then refusal note or cleared line, joined by a blank line. It is stored and added back exactly as delivered. A later note on the same carrier, for example on a retry, follows the earlier ones and never rewrites them. The comparison with the last delivery and the memory update happen in one synchronous step after the request's last wait, so two concurrent requests each record their own carrier.
   - **Standing text.** A resume capsule or refusal note is delivered again when its text differs from the last one delivered in the session, or when the carrier of that last delivery is not in this request with its note, which covers compaction, a reverted message, an evicted carrier, a restart and a fork. A capsule lookup that times out adds nothing. A capsule or refusal left out as unchanged counts as delivered, and an armed capsule is consumed.
   - **Cleared refusal.** A delivered refusal stays in history after it stops applying, so one fixed line is delivered in the same way: `Agent Progress note (delegation): the earlier delegation refusal no longer applies; read the current plan before you declare or link.` It is the one text this change adds. It is delivered only after a successful, complete refusal read that finds no refusal, while the last refusal delivered is still in this request with its note; a read that fails or is incomplete adds nothing. The cleared line counts as the last refusal delivered, so the same refusal returning is delivered again. A resume capsule that becomes empty after a successful lookup gets no cleared line: the capsule already says to read the current state first, and the earlier capsule staying in history is accepted.
   - **Memory bound.** At most 128 sessions, least recently used first, and per session at most 64 carriers and 64 KiB of note text. Entries whose carrier is absent from the latest request are evicted first, then the oldest. A carrier evicted from the memory, a restart or a fork loses its note once, which changes the prefix once from that message on, and is accepted; the standing-text rule then delivers the current capsule or refusal again.
4. **What stays as it is.** The tool set, the tool description, the skill text and the note added once to a completed tool result already stay identical after their first send. On every path that removes the section (capture off, report tool unavailable, source unverified, caller lookup failed, an epoch change, disposal, or a failure in the hook), every note the companion added is removed from that request too, so a disabled or unverified context exposes none. The session's memory is cleared only when capture is turned off, the source binding changes or the companion is disposed; a transient failure, or a request without the report tool, keeps it, and the notes come back with the section. Turning those on or off still changes the prefix once. Compaction already rebuilds the prompt.
5. **Tests.** A context-hook test runs consecutive requests built from a growing stored history across a hint trigger, a capsule revision, a capsule lookup timeout, and a refusal appearing, clearing and appearing again, on a user carrier with and without an identifier and on a tool carrier. It asserts that the system array is identical each time and that each request's messages, including every note, are a byte-identical prefix of the next request's. Further cases: removal followed by the section coming back, a missing carrier or compaction causing the standing note to be delivered again, a failed refusal read adding no cleared line, and a reused tool call identifier in a later turn not receiving the earlier note. The native activation driver also checks the outgoing requests of a real plan-file write continuation: the hint arrives inside the last tool result, the system section is unchanged, the next outgoing request repeats that tool result with the hint, and the stored conversation does not contain it; it records whether the host's user messages carry an identifier. Prompt-cache hit rates are not measured: that needs a live provider.

## 9. Delivery, verification and rollback

Each numbered task group is one pull request into the development branch with its documentation, its three-language copy where copy changes and its tests, and passes portable CI alone. Every defect gets a regression test that fails before its fix. No generated output and no version change is committed in these pull requests.

Group 8 touches only the companion's context hook, its tests and the guides' statements about where the section goes, and is independent of every other group. Groups 2, 4 and 6 touch disjoint source and test files, and different lines of the guides, and can start together. Group 5 touches only the large-library driver, gate and their tests and is independent of every other group. Group 3 follows group 2, because both change the end of the bulk run in the shared controller and extend the same controller test file; it also follows group 4, which rewrites the same line of the Tidy result statement in `docs/ui.md`. Group 1 follows groups 2, 3, 4 and 6 and merges last: it shares the controller with group 2, the cleanup model with group 4 and the bulk-count paragraphs of the two guides with group 6, and it changes how the end of a run hands its receipts to the selection, in the lines groups 2 and 3 change before it, and extends the same controller test harness as group 3.

Interface checks use the controller, search and selection unit harnesses, and source-built disposable guests with real browser input for the result line in three languages and the keyboard pass. Service-facing checks use the disposable cleanup fixture. They are synthetic-host evidence, not native-host or physical-phone acceptance.

Rollback is by reverting pull requests in reverse order. Nothing is stored and no contract with the service or with older guests changes.

**Archiving.** This change's requirement deltas modify capabilities introduced by the 1.5.0 and 1.5.1 changes, and neither is archived yet. The 1.5.2 release pull request archives the 1.5.0 change, then the 1.5.1 change, then this one, in that order; each archive builds the base spec the next one's deltas apply to. The pull requests of groups 1 to 6 archive nothing. Before each archive, that change's task list is reconciled: a task whose work shipped is ticked, and a task that did not happen stays unticked with a note saying whether it is deferred, superseded or out of scope. An archive that refuses a delta is a finding to resolve in the delta, not a reason to skip the spec update or the validation.

The chain was rehearsed on a disposable copy of the specs, and three rules follow from it. A modified requirement must keep every scenario name the spec already holds under that requirement, or the archive refuses the whole change; this change keeps them, which is why the confirmation requirement retains its "Context changes mid-run" scenario and adds the account and store case beside it, and why the result requirement keeps its six scenarios and moves the unconfirmed rules into a requirement of their own. A capability that an archive creates gets a placeholder purpose, which strict validation of the specs reports until a purpose is written. And a requirement text longer than 500 characters passes in a change's modified block but is reported once it is in a spec, so this change keeps its two modified texts below that. In the rehearsal the 1.5.0 change archived as it is. The 1.5.1 change was refused for two modified requirements that each dropped a scenario name the 1.5.0 specs hold, and it left four requirement texts above the limit. The two scenario names and all four texts are corrected in the 1.5.1 change inside the release pull request, before its archive, so that strict validation passes after each archive and not only after the last; this change's result requirement then replaces one of the four. With the two names restored and the four texts shortened in the copy, and a purpose written for each capability an archive created, the 1.5.1 change and then this one archived without a refusal, and strict validation of the specs reported nothing after each of the three archives.

Promotion to the distribution branch follows the release pull request, so it is listed after the archive in the task list.
