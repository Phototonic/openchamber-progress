## Status is not mutation authority

Use the existing selection and journal readers. The terminal exception applies only on the ordinary read-only Setup status path, after a non-absent selected binding matches the journal binding and the format-3 parser has validated completion. The same Store observer serves inspection, review and step-effect callers: keep their strict comparison as the default. Do not normalize `device` in the claim producer, canonical serialization, consent digest or shared platform identity helpers.

Compare the live directory and database against the same evidence as before: a creation checkpoint when present, otherwise the reviewed object. Ignore only the recorded `device` member in those two historical comparisons. Keep claim shape, the recorded inode and birth-time comparison (including the existing representation where birth time is unavailable), canonical paths, expected presence and object kinds. Still inspect the fixed SQLite sidecars and reject unsafe files and links; do not require all sidecars of an existing Store to be absent.

## What “Store identity” establishes

The documented terminal contract remains: verify the selected source, Store identity, schema, private objects and actual capture setting. Read-only Store open checks the SQLite header, supported schema and product. The Store envelope gets its ID from `meta.store_id`, not from the path or journal. Fresh observation matches this ID and source to the journal; binding verification matches the ID, source ID, canonical roots and verification bit to the selection. Keep the existing run-storage and private expectation reads: missing expectation is not a matching load, and a different loaded fingerprint is not by itself a reason to reject the Store.

Apply the same historical comparison on Linux, macOS and Windows; do not detect filesystem types or query new volume identifiers. On POSIX, canonical paths, owner and private modes remain mandatory. On Windows the journal device field can represent a persistent volume serial: ignoring it here removes that historical cross-volume distinction, **not** the live device/file-ID alias checks, link protections or canonical Windows path checks. Windows continues to rely on default profile permissions; this is not an ACL check.

A different logical Store still fails. A snapshot or volume clone preserving the Store ID, source and remaining filesystem evidence at the selected path need not be distinguishable from its original. Verified status is therefore not proof of the same physical volume or latest historical contents. It authorizes no write; subsequent data and mutation requests keep their independent checks. This limitation is why the rule must not be reused for Resume or removal.

## Panel feedback

Classify the refusal where the guest knows it is observing Setup admission, rather than changing the global fallback for HTTP errors. A fixed Setup-specific diagnostic such as `managed-migration-conflict` is positive evidence; HTTP 503 alone, an arbitrary string or a prior successful health read is not. Preserve the diagnostic for troubleshooting. Use the existing localized Setup guidance and More → Setup entry where possible. Keep specific storage failures, host/proxy failures, the starting-contention exception and genuinely unconfigured state distinct. Do not add a data probe, automatic repair, retry loop or new wire field.

## Compatibility and rollback

A fixed service can verify existing completed journals on the next status read, even with an older guest. An updated guest can explain a refusal from an older service that reports it; it cannot repair that service's verification. Rolling back the service can restore the old false refusal; rolling back only the guest can restore the old message. Neither needs a journal rewrite, database downgrade or reinstallation.
