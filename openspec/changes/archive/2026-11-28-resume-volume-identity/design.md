## Which identity is available?

| Candidate | What it proves | Decision |
| --- | --- | --- |
| Node `stat` / `statfs` (Linux and macOS) | `stat` supplies the existing device, inode and birth-time claim. [`StatFs` in Node 24.19.0](https://github.com/nodejs/node/blob/v24.19.0/lib/internal/fs/utils.js) returns type, block sizes, block and file counts. `bigint` changes precision, not the fields. No `f_fsid`, volume UUID or subvolume ID. Even the [native `f_fsid`](https://man7.org/linux/man-pages/man2/statfs.2.html) has no portable cross-boot identity guarantee. | Keep the native object checks. Neither filesystem type, capacity, canonical path, copied marker nor matching Store contents distinguishes a snapshot. |
| Linux btrfs mount and device metadata | A [btrfs subvolume ID](https://btrfs.readthedocs.io/en/stable/Subvolumes.html) is persistent within one filesystem. A snapshot is a different subvolume even when its objects keep their inode numbers. The kernel [prints the mount root's `subvolid`](https://github.com/torvalds/linux/blob/master/fs/btrfs/super.c); this does **not** identify a nested subvolume reached as a directory. | Use only when the specific target is proved to be in that mounted subvolume. Combine its numeric ID with independently verified backing identity. |
| Volume UUID alone | On Linux, unprivileged Node filesystem reads can use [btrfs sysfs](https://btrfs.readthedocs.io/en/stable/ch-sysfs.html) and, when available, [udev persistent links](https://github.com/systemd/systemd/blob/main/rules.d/60-persistent-storage.rules.in). Subvolumes share the filesystem UUID; even `(filesystem UUID, subvolid)` can be copied in a block image. | Require independent identity of the backing disk/partition as well. Do not treat a device-node name, mount path or `by-uuid` link alone as proof. |
| Direct OS APIs | Linux [`STATX_SUBVOL`](https://man7.org/linux/man-pages/man2/statx.2.html) or [`BTRFS_IOC_GET_SUBVOL_INFO`](https://github.com/kdave/btrfs-progs/blob/devel/libbtrfsutil/README.md) can identify nested subvolumes; the latter can read the subvolume's **own** UUID without elevation on supporting kernels. macOS [`getattrlist(ATTR_VOL_UUID)`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/getattrlist.2) is a volume query; [APFS snapshots have their own identity](https://support.apple.com/guide/disk-utility/view-apfs-snapshots-dskuf82354dc/mac). | These are not Node 24 filesystem APIs. Neither spawning `btrfs`/`diskutil` nor shipping a native binding is justified for the verified-mount case. No macOS snapshot-safe identity is established here. |
| Explicit recovery instead | Keeping the operation stopped is safe on all platforms but does not make an unprovable original resumable. A fresh review or “this is the original” click on the same copied bytes proves nothing new. | Use normal explicit continuation where proof exists; elsewhere retain everything and document separate recovery, not a force option. |

## A bounded Linux witness

Restrict enrollment to an ordinary, directly mounted btrfs subvolume on a single identifiable local block device. Collect a versioned private fingerprint of **filesystem UUID, persistent subvolid and off-filesystem disk identity with its partition extent (or whole disk)**. A disk world-wide name (WWN) identifies the backing device independently of copied filesystem metadata. The same WWN without a partition distinction is not enough. Store the comparison fingerprint, not a public inventory of devices.

1. Work from Setup's already validated canonical target or its verified containing directory, never from caller-provided mount data. Join the opened directory's [`mnt_id`](https://man7.org/linux/man-pages/man5/proc_pid_fdinfo.5.html) to the process's [mount table](https://man7.org/linux/man-pages/man5/proc_pid_mountinfo.5.html); use that number only for this observation. Parse escaped paths and the superblock options of the identified entry. Verify the accessible mount root really is the indicated subvolume root (including its root inode and current mount identity), not a bind-mounted subdirectory. Check the path from there to the target: no intervening mount or nested subvolume root, including a nested root *at* the target, or file overmount. Match current device/object observations across this check. Do not equate the mount table's major/minor with the target's `st_dev`, or select the first/longest string prefix. Do not open/close extra raw SQLite database descriptors during an active SQLite transaction to obtain mount information.
2. Correlate the entry's actual block source with the single mounted filesystem member in sysfs, and that block object with its stable disk/partition identity (for example a system-managed WWN link and kernel partition start/length). Filesystem-UUID links can aid lookup; validate membership, not just a plausible UUID. Use system-owned metadata, without opening the block device. Exclude stacked/loop devices, multi-device or degraded/seed/temporary-FSID cases, ambiguous mount mappings and missing, inconsistent or inaccessible identifiers. No inference from a neighboring mount. This assumes truthful OS/storage identifiers; restoring an entire image *in place* to the same backing extent or spoofing hardware is not detectable as a change of device. This is not general rollback detection.
3. Limit bytes, directory entries, paths, descriptors and time **before** materializing or acting on metadata. Close descriptors on failure. Deduplicate reads within a single read-only validation batch; never cache authority across a write or request. On non-Linux and non-btrfs take the existing strict path without probing Linux device inventories. Missing evidence at initial review leaves existing strict Setup available; loss, overflow or inconsistency after a witness is frozen never authorizes fallback.

### How CI can exercise the real reader

A bare `/dev/loop` mount is useful for making a test image, but is deliberately **not** an eligible backing disk. Use a disposable Ubuntu runner to format the image on a loop device, then detach it. Present that file as a whole SCSI test disk using Linux's [local loopback target](https://linux-iscsi.org/wiki/tcm_loop) and a [FILEIO backstore](https://github.com/open-iscsi/targetcli-fb/blob/master/targetcli.8). The SCSI logical unit's WWN comes from the target, not the bytes in the image; ordinary kernel/udev interfaces must report it to the unmodified service. Re-present an offline block copy with a **different** unit WWN, never alongside the original filesystem UUID. This tests OS-reported backing identity, not physical hardware authenticity. No test-only identity injection, fabricated `by-id` link or product exception for loop devices. Only the fixture controller provisions storage; the service and tests run as the ordinary runner user.

## Record before the interruption; compare at the effect boundary

Use the existing format-2/3 journal families with strictly recognized, optional versioned evidence in the immutable reviewed `legacy` / `fresh` facts, covered by `managedTargetDigest`. Bind proof only to paths derived by the existing target/layout owners; do not follow new paths from the journal. Cover the Store directory and database, and independently cover each affected discovery, payload, publication and history location. Where several paths share one fingerprint, still prove each path's membership. For an absent target, use its verified existing containing directory for placement; this is not an object claim or proof of creation. Require a new object to be on the reviewed storage as well as satisfying the existing exclusive creation, intent and checkpoint rules. Ensure the database and effect destinations belong to the proven storage even on the receipt-only branch, which otherwise proves logical Store identity and the history file, not the database's physical placement.

Only a **live-versus-historical** comparison may accept a different device for a covered path; the recorded fingerprint must match positively even if the old device number happens to match. Preserve inode, recorded birth time, type, canonical path, presence, ownership/mode/link, manifest/digest, schema, Store/source, expectation and capture checks. For another root on a different device use its own evidence, or its unchanged exact checks, never the Store's proof. Keep live-to-live race checks and all saved-to-saved equality (including original claims versus intent, immutable consent, request digests and receipts) exact. Do not normalize or rebase historical device numbers.

Revalidate after restart and at every existing write boundary, including first-journal sibling settlement, publication, unlink, rmdir and the subsequent history append. Reading status never settles the journal. Resume itself performs no Store/removal effect. A lost reply, fresh proof of identity or an already absent file is not new authority to enable capture, skip a step or repeat deletion. Separate inability to establish identity **before** a write (refuse without changes) from failure **after** an already authorized effect (existing uncertain-intent handling; no rollback claim).

## Compatibility, recovery and rollback

Old-shaped records keep their original bytes, target digests and device comparisons. Do not learn a missing witness from the post-reboot target, add it on replay, or rewrite an old operation at startup. A freshly consented format-1 upgrade may start a new format-2 operation only through the existing manifest/receipt proof; no upgrade circumvents a previously retained mismatch. Unsupported evidence versions and malformed records refuse. Older strict readers reject an enriched journal, including a completed one; roll back code only, retain all private state and return to a compatible service to continue. Wire requests, capabilities and guest actions do not change.

On a proved original, reopen Setup and use its advertised Continue/Resume; review an uncertain capture effect as before. If identification fails, stop, preserve the journal, Store, discovery files and history, and check independently that the original disk and subvolume are mounted at the reviewed locations and the service can read the original identity evidence. Retry explicitly only after restoring those conditions. If the original cannot be proved, or an older journal already saw its device change, keep the refusal and obtain separately authorized recovery using only a sanitized stage/code for support. Do not edit device numbers, remove locks, repoint Setup at a snapshot or reset capture. No promise of in-place recovery without pre-interruption evidence.
