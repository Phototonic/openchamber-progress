# Design

## 1. Existing owners and constraints

The existing Store transaction owns expected-revision mutation, task authority, snapshots, contributions and replay receipts. Durable next-dispatch intent is in `runs_intents`; its disposition is written back to the declaration's receipt. `afterRun` currently converts the intent into a link at the declaration revision. Any intervening plan mutation therefore conflicts. The intent is consumed even on refusal. The service/UI expose assignment provenance, not pending intent, and selected-plan detail caching alone cannot observe declaration/cancellation because these do not advance plan revision.

Work Status currently reads the selected session and one selected plan's detail. Its blocked chip calls every blocked task “needs you”; that is not the new person-facing category rule. The board already supports bounded cross-plan search, on-demand detail and task reveal. The existing blocker timing owner derives exact/lower-bound intervals from reported history, never activity or browser wall time. Reuse these boundaries rather than fetching every plan's full detail on each refresh.

The common UI controller owns source/account/runtime retirement, hidden-frame pause and the existing 3-second/8-second failure cadence. Phone and inbox work must use this owner, including its ordinary session-action pin/reset behavior. `openSurface(surfaceId)` has no item payload. Do not invent deep-link arguments or persistent cross-frame mailboxes.

## 2. Phone contract and layout

The published SDK 2.7.0 parser/declarations lack the mobile fields. Published SDK 2.7.1 and the OpenChamber 2.7.1 tag support `contributes.panel.mobile: true` and object-form `contributes.page.mobile: true`; omission, not `false`, is the non-opted-in form. Upgrade only that SDK pin and lockfile. Verify installed declarations after dependency provisioning and validate manifests with the actual SDK and host installer; do not weaken exact manifest tests.

`ready.device` is optional. In 2.7.1 it contains `formFactor` (`phone`, `tablet`, `desktop`), `pointer` (`coarse`, `fine`), numeric screen `insets` (`top`, `right`, `bottom`, `left`) and numeric `keyboard` occlusion height. The host re-sends ready on rotation/keyboard changes. Treat these as presentation hints, never identity, permissions or proof of visibility. Absence retains responsive CSS and existing behavior; do not infer shown/hidden events from dimensions.

Keep the shared views. At phone width, arrange board navigation and detail in a readable single column, compact/wrapping plan controls, safe-area-aware sheets and visible back/close actions. Keep essential actions reachable above keyboard occlusion. Coarse-pointer controls target at least 44 CSS pixels. Task navigation, plan selection, dependency inspection, map pan/zoom and return-to-list remain operable without hover. A long-press may supplement, never replace, a labelled tap/keyboard action. Use current focus and selection owners; no phone-only progress store. Layout work owns CSS/map interaction while content work owns inbox/delegation mounts; the initial interface checkpoint fixes class/hooks and device delivery to avoid concurrent structural edits.

Inventory Work Status, report tool rows, mentions, sidebar indicators and background actions without opt-in. Panel opt-in covers the phone workspace tab, plus-menu entry, chips and actions opening that panel. Page opt-in covers More and full-screen/back navigation. Record observed routes and versions, not a blanket “all mobile” claim. The existing same-item **Show current session** limitation remains: an identical retained action cannot re-pin the same frame after reset until a different target or reload (OpenChamber issue #6938). Verify its actual phone behavior; no visibility heuristic workaround.

Use a disposable test-package projection with mobile flags for acceptance. Do not ship those flags until the corresponding physical-phone checks pass. If one surface fails, retain its omission and hold that release scope for owner disposition rather than silently declaring completion.

### Conditional Work Status research

Only if the phone design exposes a concrete iframe limitation, spend at most 45 minutes comparing the host-drawn `statusSection.source` contract with the existing display. SDK 2.7.1 limits it to 16 rows and 6 chips per chip content; the host owns polling. Evaluate source/selected-session identity, language, task navigation, controls, completeness and refresh budget. Produce a short go/no-go note in the phone compatibility discussion. Default is retain the iframe. A promising result informs a later approved change; it does not authorize a second status implementation here.

## 3. Needs you read projection

Scope is all active, non-archived/non-deleted plans in the currently verified service source, independent of the selected session or directory. Label that broader scope. Source identity must match the host/service binding; no fallback to another source. Keep ordinary selected-session progress separate.

Classify current reported task state only. Valid current decision/review annotations enter Needs you. Dependency/external/other, absent, unknown or invalid annotations on explicitly blocked tasks enter Also blocked, using honest fixed labels and no unsafe malformed text. Groups never enter either list. Identity is `(source, plan, task)`; a row occurs once. Count only the first group. Closing a plan or resolving/removing a task removes it on the next accepted read. Show reported reason/next action literally; unknown values stay unknown. Reuse blocked history timing with exact/lower-bound/unavailable labels, and the service-clock/monotonic client anchor. Do not treat the latest blocker edit as a new waiting interval.

Add a capability-gated, bounded read projection, not a durable inbox table. Its contract checkpoint defines shared TypeScript DTOs for store/binding identity, source, plan revision/cleanup, task facts, group, optional timing, coverage and opaque continuation. Use keyset traversal and admission/byte bounds from plan-task search. Freeze the numeric budgets with the interface before independent consumers start; use existing `SEARCH_LIMITS` and blocker timing budgets rather than an unbounded scan. Never silently drop capped records. Stable pagination must eventually reach every eligible task; changing pinned records must conflict/restart, not splice revisions. A multi-request traversal is labelled observed current data, not an atomic source-wide snapshot.

Transport: attach the bounded first summary window to opted-in first-page `/v1/plans` reads, without changing their normal session/directory plan list. Older services ignore no new request silently: advertise capability and request the extension only when supported. While board search freshness replaces the list read, its existing `/v1/search-state` response can carry the same optional summary. Fetch subsequent inbox windows through a bounded read-only `/v1/needs-you` route on explicit open/continuation. When the inbox is the active reading, use the existing refresh slot for its freshness, never add an interval, background subscription or per-task poll. Ordinary list readers, including composer actions, remain unchanged. Summary work is once per scheduled cycle, not once per list page.

Exact totals require complete gap-free coverage; otherwise show qualified known counts or unavailable coverage, never a false zero or exact total. A complete empty first group says no reported items need the user even when Also blocked is nonempty. Unsupported services show unavailable/upgrade guidance rather than a fabricated empty inbox. History timing is requested only for displayed inbox rows, with bounded per-plan work and no history fan-out for the compact count.

The compact inbox is a discoverable section at the start of panel and board, independent of the ordinary selected-plan body. Work Status's line opens the supported panel; the compact section is already there, so no unsupported navigation payload is needed. More rows are explicit continuation. Selecting a row enters a clearly labelled source-wide inbox reading and revalidates current plan/task before revealing the canonical task. It does not alter the host session, persisted session pin, task status or draft. Back returns to the prior normal reading. Keep this ephemeral cross-plan reading separate from the existing action pin; context/source changes retire both requests and navigation targets.

## 4. Delegation concurrency and visible disposition

Adopt both prevention and explanation. Declaration still requires the exact current revision and coordinator authority. Binding still requires verified same-source native ancestry, correct dispatch, capture generation, active visible plan and conflict-free assignments. There is no child authority until binding and no automatic preparation turn.

At binding, the same write transaction may advance the derived link's expected revision only after proving every intervening committed revision is irrelevant to the declared tasks. Preserve the original request/replay hash. Require unchanged structural revision and active lifecycle; inspect the bounded retained interval and contribution/assignment facts, not just endpoint equality. Any declared-task touch, assignment change affecting those tasks or coordinator authority, structural operation, close/reopen, cancellation, cleanup, capture invalidation or missing/corrupt/incomplete proof refuses. Unrelated task reports may pass. Ignore mechanical whole-plan annotation validity-marker rollover when deciding a task was touched; do not ignore meaningful blocker/status/reporter/assignment changes. Changed-then-restored tasks still conflict. If the interval exceeds existing bounded history admission, refuse visibly rather than guess. Legacy intents without sufficient proof retain strict-revision behavior.

Use existing declaration receipts as durable disposition evidence. Add bounded, backward-readable source/coordinator/plan/task/dispatch metadata to the delegation receipt as needed for exact identification; keep the original replay receipt authoritative. Do not change the exact run-table DDL or add fields to strict public run-row payloads. Reuse receipt/run/activation owners for a bounded latest-disposition read, filtering the actual coordinator and source. Limits and incomplete lookup must remain explicit; do not present lack of proof as successful binding. On the next eligible coordinator context, a refused declaration identifies affected tasks and gives the reason plus re-declare-at-current-revision or explicit-link recovery. Repeated identical hints can be coalesced in existing context lifetime; receipt evidence remains durable. Restricted tool contexts remain restricted.

Expose a read-only, capability-gated delegation overlay for plan detail and an independent disposition token on list metadata. The token covers current intent/disposition and eligibility, not only progress revision; declaration, reservation, cancel and invalidation must retire the cached overlay on the normal refresh even when progress does not advance. The common bounded validity predicate is used for binding and read eligibility. Reads never settle or mutate an intent. Pending/reserved eligible intent renders “Next sub-agent will take this” faintly on affected tasks; invalid/retired/conflicted intent cannot render that note. A conflict is separately labelled, not converted to pending. Bound/cancelled/closed/invalidated state clears the pending note. An older service gives no note, not a guess from agent activity.

## 5. Atomic finish

Extend the existing request/parser/tool schema so `finish` optionally accepts the same nonempty 1–50 unique task changes as `change`. Omission retains the current behavior; an explicit empty array remains invalid. Reuse the task validation path, including group/unknown-ID hints, blocker validation and current expected revision. Finish remains coordinator-only; this does not enable attributed relay or child finish.

Within the existing transaction apply explicit changes before testing the requested outcome. `finished` still needs nonzero actionable work and no remaining actionable tasks; empty/all-skipped work cannot finish successfully. `cancelled`/`failed` retain their outcome semantics. Commit one snapshot revision, unchanged structural revision, direct coordinator contribution for changed tasks, and the full-input receipt. Any validation, authority, conflict or storage failure commits neither component. Current blocker annotations clear on close as before; history retains earlier facts. Identical accepted retries return their original result, while changed/omitted changes under the same operation identity refuse. An old writer rejects new input and must never claim combined success; any fallback is deliberate after a fresh read, not field stripping.

## 6. Receipt index and compatibility

Choose the ordinary `(source, oid)` index. Keep the existing `_handoffChild` JSON predicate and the cross-plan lookup. Claims/assignment state cannot prove receipt absence: pruning, session-only claims, unlink/revise and combined-to-bare retry must retain their current refusals. Do not use those facts to skip the lookup.

This is a physical schema addition, not “no schema change.” Keep base protocol/schema version 2, base tables and receipt representation unchanged. Give the index a dedicated non-`runs_*`, non-`cleanup_*` name (for example `receipts_source_oid`), avoiding those modules' exact-DDL namespaces. Install/validate it transactionally during authorized writable initialization/companion activation; new database creation includes it atomically. Reads and setup inspection never install it. Existing stores without it remain readable. Validate an existing owned name's table, column order, uniqueness and partial/expression properties; do not accept a foreign object merely because `IF NOT EXISTS` succeeds. Failure rolls back and surfaces the existing storage/schema error without dropping or rebuilding unrelated objects.

The current base Store checks schema version/product rather than an all-object whitelist; run and cleanup validators compare only their own prefixes. That supports this additive approach but is not downgrade proof. Test unmodified released readers, ordinary writers, combined-handoff writers and cleanup on an indexed store, plus reactivation after rollback. Keep the harmless index on code rollback; no automatic down-migration or receipt rewrite. A proven incompatible historical reader/writer holds this capability for amendment rather than broadening its schema allowlist or erasing data.

Use actual `EXPLAIN QUERY PLAN` for the unchanged lookup and synthetic workloads around 1,000 and 50,000 receipts, including reused operation IDs across plans/children. Record comparative lookup and write-transaction timing and index build/storage cost. The reported baseline timing is a lead, not measured evidence. Assert indexed candidate selection and unchanged results; do not add a brittle millisecond gate. An expression index is not authorized unless evidence and owner approval change this decision.

## 7. Verification, delivery and rollback

Backend feature checks use source-built disposable companion fixtures. UI feature checks use source-built temporary guests and real browser screenshots where layout is exercised. Neither depends on stale tracked bundles. After source acceptance, one integration owner updates shared guides/guidance, versions/release notes and all transitively affected outputs, then verifies the exact built distribution. Shared UI adapter/i18n/source changes and the SDK update also affect `background/main.js`.

Use disposable OpenChamber 2.7.1, independent OpenCode 2.2.7 and a credential-free scripted provider with synthetic HOME/XDG. Real dispatch tests, not actor seeding, prove binding and coordinator notices; actual HTTP tests prove service authorization and read-only behavior. Real-browser touch emulation supports, but never replaces, physical phone app/browser checks over the host's supported authenticated route. Only the owner can operate that device/authentication boundary; no authentication is copied into fixtures or evidence.

Before promotion, require actual supported Git/folder/ZIP installation, below-floor refusal, lifecycle/upgrade/rollback and portable CI on stable inputs under `CONTRIBUTING.md`. Prepare 1.4.0 through the existing version source and curated release-note format; publishing still requires maintainer approval. Roll back matched source/generated/manifest changes, retain database/receipt history and the compatible index, and withdraw mobile flags for a failing surface. Reuse unaffected evidence, but never evidence from before a relevant source, bundle, SDK or manifest change. Incomplete physical or native acceptance remains visible, not a pass.
